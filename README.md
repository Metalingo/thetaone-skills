# Thetaone Skills

AI에게 개발을 맡길 때 사용하는 7가지 작업 지침입니다. 막연한 요청을 구체화하고, 기능을 만들고, 배포 후 제대로 동작하는지 확인하도록 돕습니다.

**지금 필요한 스킬 하나부터 사용하세요.** 모든 단계를 순서대로 거칠 필요는 없습니다. 에이전트가 코드와 문서를 확인하고, 여러분의 판단이 필요한 부분은 질문합니다.

## 지금 어떤 도움이 필요한가요?

| 내 상황 | 사용할 스킬 |
| --- | --- |
| 무엇을 고쳐야 할지, 어디까지 만들지 아직 막연해요 | `clarify` |
| 오류 제보나 기능 요청을 Linear에 등록하고 싶어요 | `create-linear-issue` |
| 작업 티켓이 있어요. 구현부터 PR 리뷰까지 맡기고 싶어요 | `implement` |
| 작업 내용을 GitHub에 올리고 팀원에게 검토받고 싶어요 | `smart-commit` |
| 요청대로 만들었는지, 문제가 없는지 검토하고 싶어요 | `review-pr` |
| 배포한 기능이 실제로 잘 동작하는지 확인하고 싶어요 | `verify` |
| AI의 설명이 어려워요. 쉽게 설명해 주세요 | `ste-explain` |

아래 예시처럼 **스킬 이름과 원하는 일**을 함께 말하면 됩니다. 설치 방법은 [설치하기](#설치하기)를 참고하세요.

## 어떤 순서로 사용하나요?

- **무엇을 해결할지 모호하다면:** `clarify`로 문제와 완료 기준을 정리한 뒤, 작업을 등록하려면 `create-linear-issue`를 사용합니다.
- **등록할 작업이 이미 명확하다면:** 바로 `create-linear-issue`를 사용합니다. 필요한 내용은 자체적으로 확인하므로 `clarify`를 먼저 쓸 필요는 없습니다.
- **구현을 시작하려면:** 기존 티켓의 링크나 번호를 `implement`에 전달합니다. 이슈를 만들었다고 구현이 자동으로 시작되지는 않습니다.

`implement`를 호출하면 다음 순서를 기본으로 완료합니다. 커밋이나 PR 생성을 따로 요청하지 않아도 됩니다.

```text
implement → smart-commit(커밋·push·PR) → review-pr
```

배포가 끝나면 `verify`로 실제 동작을 확인합니다. `create-linear-issue`, `smart-commit`, `review-pr`은 각각 단독으로 사용할 수도 있습니다. 단독 호출하면 해당 작업을 마치고 결과를 보고합니다.

## 스킬별 사용 예시

### clarify · 무엇을 해결할지 정하기

> “clarify로 이 제보를 정리해줘. 사용자가 겪는 문제와 이번에 고칠 범위를 명확히 하고 싶어.”

현재 어떤 일이 일어나는지, 어떻게 바뀌어야 하는지, 무엇을 확인하면 완료로 볼지 정리합니다. 이미 정한 내용은 다시 묻지 않고, 중요한 선택이 남아 있을 때 질문합니다.

정리가 끝나면 작업을 Linear에 등록할 수 있습니다. 이미 티켓이 있고 구현을 원하면 `implement`로 이어갑니다. 문제 정리만 요청했다면 여기서 마칩니다. [스킬 지침](skills/clarify/SKILL.md)

### create-linear-issue · 팀이 착수할 수 있는 작업 등록하기

> “create-linear-issue로 이 오류 제보를 조사해서 Linear에 등록해줘.”

코드와 관련 자료를 확인하고, 작업이 필요한 이유와 완료 기준을 이슈에 담습니다. 큰 작업은 **각각 결과를 확인할 수 있는 작은 작업**으로 나눕니다. 이를 슬라이스라고 하며, 먼저 끝나야 하는 작업도 표시합니다.

등록한 이슈 링크를 전달하고 마칩니다. 구현은 작업자가 별도로 요청합니다. Linear 연결이 없으면 초안을 준비합니다. [스킬 지침](skills/create-linear-issue/SKILL.md)

### implement · 티켓을 받아 구현부터 PR 리뷰까지 마치기

> “implement로 이 Linear 이슈를 작업해줘: [이슈 링크]”

Linear 이슈 같은 기존 작업 티켓을 전달하면 **계획·구현·테스트·커밋·push·PR 생성·리뷰까지** 진행합니다. 단계마다 따로 요청하거나 확인해 줄 필요는 없습니다. 코드는 별도 작업 공간인 **worktree**에서 수정하고, 계획과 검사 결과를 문서에 남깁니다.

작업 중 새 사실이 드러나거나 기존 가설·근거가 틀려 방향을 다시 정해야 할 때 질문합니다. 일반적인 구현 문제나 테스트 실패는 에이전트가 조사하고 해결합니다.

완료 후 PR 링크, 검사 결과와 리뷰 판정을 보고합니다. 리뷰를 마쳤다는 뜻이 곧 승인을 받았다는 뜻은 아닙니다. 변경을 프로젝트에 합치는 머지와 실제 서비스에 반영하는 배포는 기본 작업에 포함하지 않습니다. [스킬 지침](skills/implement/SKILL.md)

### smart-commit · 작업을 기록하고 검토 요청까지 만들기

> “smart-commit으로 이번 변경을 커밋하고 PR까지 만들어줘.”

변경 내용과 이유를 기록하는 **커밋**, 그 기록을 GitHub에 올리는 **push**, 팀원에게 검토를 요청하는 **PR(Pull Request)**을 한 번에 진행합니다. 기존 PR이 있으면 새로 만들지 않고 갱신합니다.

로컬에 기록만 남기려면 “커밋만”, GitHub에 올리기까지만 원하면 “PR 없이 push까지만”이라고 요청하세요. PR 생성만 필요한 경우도 이 스킬을 사용할 수 있습니다. PR을 만드는 것만으로 변경이 반영되거나 배포되지는 않습니다. [스킬 지침](skills/smart-commit/SKILL.md)

### review-pr · 요청대로 만들었는지 검토하기

> “review-pr로 이 PR을 검토해줘. 이슈의 완료 기준을 충족하는지 확인해줘.”

요구사항을 충족하는지 먼저 확인하고, 오류 가능성과 기존 기능에 미치는 영향, 테스트를 검토합니다. 문제가 있으면 발생 조건과 근거를 설명합니다. 팀원이 남긴 리뷰 의견이 타당한지 확인할 때도 사용할 수 있습니다.

검토 결과를 보고하며, 수정이나 GitHub에 리뷰를 게시하는 일은 요청 범위에 따라 진행합니다. [스킬 지침](skills/review-pr/SKILL.md)

### verify · 배포 후 실제 동작 확인하기

> “verify로 이 변경이 테스트 환경에 배포됐는지 확인하고, 이슈의 완료 기준을 검증해줘.”

먼저 목표 환경에 변경이 반영됐는지 확인합니다. 이후 실행 기록인 **로그**와 오류·사용 기록 등을 살펴봅니다. 오류 기록이 없다는 이유만으로 성공이라고 판단하지 않고, 해당 기능이 실제로 실행됐는지도 확인합니다.

결과는 **통과 / 실패 / 검증 불가**로 보고합니다. 확인할 기록이 부족하고 이를 남기는 기능을 추가해야 한다면 후속 Linear 이슈를 만듭니다. 이 스킬이 코드를 고치거나 배포하지는 않습니다. [스킬 지침](skills/verify/SKILL.md)

### ste-explain · 이해하고 판단할 수 있게 설명하기

> “ste-explain으로 이 결과를 쉽게 설명해줘. 확인된 사실과 아직 모르는 부분을 구분해줘.”

결론부터 설명하고, 낯선 용어를 풀어 씁니다. “테스트를 통과했다”와 “실제 서비스에서 동작을 확인했다”처럼 서로 다른 상태를 구분합니다.

다른 스킬도 설명이나 질문을 할 때 이 스킬을 함께 사용합니다. [스킬 지침](skills/ste-explain/SKILL.md)

## 설치하기

사용하는 에이전트에 맞춰 **한 가지 방식**을 선택하세요. 같은 스킬을 두 방식으로 설치하면 중복될 수 있습니다.

### Codex 및 다른 에이전트

스킬을 사용할 프로젝트의 터미널에서 실행합니다.

```sh
npx skills@latest add Metalingo/thetaone-skills
```

안내에 따라 설치할 스킬과 에이전트를 선택하세요. 스킬 간 연결 기능도 사용하려면 7개를 함께 설치하는 편이 간편합니다. 기존에 같은 이름의 스킬이 있다면 교체할지 먼저 확인하세요.

<details>
<summary>선택 설치와 업데이트</summary>

목록 확인과 특정 스킬 설치:

```sh
npx skills@latest add Metalingo/thetaone-skills --list
npx skills@latest add Metalingo/thetaone-skills --skill clarify --agent codex
```

여러 프로젝트에서 사용하려면 `--global`을 추가합니다. Bun 사용자는 `npx` 대신 `bunx`로 실행할 수 있습니다.

업데이트 확인과 적용:

```sh
npx skills check
npx skills update
```

업데이트 명령은 이 도구로 관리하는 다른 스킬에도 영향을 줄 수 있습니다.

</details>

### Claude Code

Claude Code 대화창에서 차례로 실행합니다.

```text
/plugin marketplace add Metalingo/thetaone-skills
/plugin install thetaone-skills@thetaone
```

7개 스킬이 한 번에 설치됩니다. 설치 후 새 세션에서 `/thetaone-skills:clarify`처럼 호출하세요.

<details>
<summary>플러그인 업데이트</summary>

터미널에서 실행합니다.

```sh
claude plugin marketplace update thetaone
claude plugin update thetaone-skills@thetaone
```

</details>

## 사용 전에 알아둘 점

스킬은 AI에게 작업 방법을 알려주는 지침입니다. 설치만으로 Linear나 배포·로그 조회 도구가 연결되지는 않습니다. 도구 접근이나 프로젝트 설정이 필요하다는 안내를 받으면 프로젝트 담당자와 확인하세요. 근거를 확보할 수 없는 검증은 **검증 불가**로 보고합니다.

현재는 초기 버전입니다. 파일 형식과 설치는 확인했지만, 실제 작업에서의 판단 품질은 계속 검증해야 합니다. 공개 marketplace는 이 GitHub 저장소에서 직접 제공하며, Anthropic 공식 디렉터리에 등재된 상태는 아닙니다.

## 기존 사용자의 업데이트

`0.2.0`부터 `create-pr`은 `smart-commit`에 통합됩니다. 파일 복사나 skills CLI로 설치했다면 업데이트 후 예전 `create-pr` 설치본이 남아 있는지 확인하고 제거하세요. 프로젝트 문서에서 `create-pr`을 호출하던 부분도 `smart-commit`으로 바꾸세요.

## 프로젝트 담당자와 기여자를 위한 안내

<details>
<summary>프로젝트 설정, 스킬 수정과 배포</summary>

스킬은 프로젝트의 기존 지침과 문서를 따릅니다. 다음 정보가 있으면 활용하기 좋습니다.

- **이슈:** 조사 기준 브랜치, Linear 팀·프로젝트, 이슈 작성 규칙
- **구현:** worktree 설정, 의존성 설치와 테스트 명령, 계획 저장 위치
- **Git·PR:** 보호·기준 브랜치, 커밋 규칙, PR 템플릿과 리뷰 절차
- **배포 검증:** 환경별 배포 버전 확인법, 로그·이벤트 위치, 완료 기준

공통 지침은 `skills/`에서 관리하고, 프로젝트별 명령은 해당 프로젝트 문서에 둡니다. 선택 설치로 필요한 스킬이 없으면 에이전트가 이를 알리고 가능한 대체 절차나 다음 작업에 필요한 정보를 제공합니다. 이미 허용한 작업 범위와 프로젝트의 승인 규칙을 따릅니다.

스킬 수정 후 파일 형식과 플러그인 구성을 확인합니다.

```sh
bun run validate
claude plugin validate .
```

이 명령은 에이전트의 실제 작업 품질을 검사하지 않습니다. 동작 변경은 대표적인 작업 사례로 별도 평가하세요.

Claude 플러그인 버전은 `.claude-plugin/plugin.json`에서 관리합니다. 플러그인 변경을 배포할 때 버전을 올리고, 검증·커밋·push 후 같은 커밋에 릴리스 태그를 붙입니다. 특정 버전을 설치하려면 실제로 배포된 태그의 GitHub tree URL을 skills CLI에 전달합니다.

Codex용 네이티브 플러그인은 아직 제공하지 않습니다. 설치 방식은 [skills CLI](https://github.com/vercel-labs/skills)와 [Claude marketplace 문서](https://code.claude.com/docs/en/plugin-marketplaces)를 참고하세요.

</details>

## 제작 배경과 라이선스

Thetaone의 language-pilot 개발 경험을 바탕으로 만들었습니다. `ste-explain`은 ASD-STE100의 명확한 설명 원칙을 응용하며, 공식 규격 준수를 뜻하지 않습니다.

라이선스는 아직 정하지 않았습니다. 외부 재배포를 확대하기 전에 라이선스를 추가할 예정입니다.
